# 小规模配对评测

目标：比较在**相同模型、相同候选论文与证据、相同 Writer 草稿**上，增加证据核验与回答限制前后的效果。这个实验是输出核验模块的配对分析，不是两个独立端到端系统的性能比赛，也不隔离补搜的独立贡献。

## 运行与采样

1. 在 `deepresearch_py313` 中运行 README 的三组联网案例命令，记录当前模型与日期。每次运行保存独立 JSON／Markdown，不覆盖旧结果。
2. `prepare` 从每个运行最后一轮的 Writer 草稿采样最多 20 条，兼顾不同运行和模型支持状态。请选择同一批、同一模型的运行文件。保留模型失败或证据不足案例，不只选好看的结果。
3. CSV 包含结论、原文、论文页码链接与机器标签。图表转录单独标记，必须回到原始页面检查行列、表头、图例及单位，不能仅依据转录文本评分。评审时建议先隐藏 `machine_status` 列，独立阅读原文和上下文再判断。

## 人工标签

- `human_support`：`supported` 原文完整支持且范围准确；`partial` 仅支持一部分或缺少重要条件；`insufficient` 无支持、矛盾、引用无效或无法核实。
- `human_relevant`：`yes` 结论对回答研究问题有实质帮助；否则 `no`。
- `reviewer`：实际人工评审者标识。不能将模型自动评分伪装成人工评审。
- `notes`：说明错误类型及判断依据。建议标注“实验范围扩大”“跨数据集错误比较”“摘要冒充全文”等。

字段为空或标签不合法的条目不计分，同时计入待完成数量。建议对有争议的结论找第二位同学复核；小样本只作案例分析。

## 指标解读

`without_verification` 将原始草稿视为直接输出；`verified_assertions` 只把最终被标为完整支持的条目计为肯定断言。

同时报告：肯定断言数量、人工判定有依据数量及比例、无依据断言数、部分支持数、与问题相关的有效回答数量、被限定或保留的条目数。比例为空表示分母为零，不表示正确率 100%。只提高正确率却大幅减少有效回答，不能声称系统整体更好。

这份脚本不把 `partial` 结论当作完整断言来计分；报告中它们仍以显著限定状态展示。单独记录运行 JSON 中的耗时、调用次数及 token 用量。核验开销已经包含在最终运行耗时中，不能将两种展示口径的耗时当作独立实测值比较。

## 补搜案例

至少保留一个 `supplemental_rounds=1` 的真实运行，检查首次缺口、改写查询、新增论文和最终停止理由。无法找到新证据也应作为有效的失败案例展示。要评价补搜本身的收益，需要另外控制搜索结果与预算进行开／关补搜实验；本版不声称已经完成该实验。

## 当前交付边界

单元测试中的人工标签为明确标注的合成测试数据，只用于验证计分程序。真实 `annotations.csv` 初始为空标签。没有完成真人标注之前，不填简历中的正确率提升数字，也不把自动化测试通过率当作论文调研准确率。
